- **Adjustments and Failsafe save through the shared save, so a save the page is left during writes every changed slot or channel with what Save was pressed with (`app/pages/setup/controls/adjustments/page.lua`, `app/pages/setup/controls/failsafe/page.lua`, `tasks/msp/save_pipeline.lua`, `docs/reference/saving.md`, `docs/pages/setup/controls/adjustments.md`)**:
  - The writes and the EEPROM write go through the shared save (`tasks/msp/save_pipeline.lua`), from what the page held when Save was pressed, instead of a chain the page queued from its own replies. A page closed before the chain had finished no longer leaves the first slot or channel changed on the flight controller and the rest unsent and unstored; a page opened again at once no longer sends that visit's values for the remaining ones, which on Adjustments switched those slots off and stored them (#574).
  - A change made on a visit opened while an earlier save was still running is no longer marked as saved when that save finishes, so the next Save writes it (#574).
  - The save's progress and outcome are shown in the shared save notice: *Settings saved.* or *Not saved*, in place of Adjustments' own message and of nothing on Failsafe. Back pressed during the save is not asked about unsaved changes; the page is left once the notice has gone. After a save that worked, Failsafe reads the flight controller again while it is still open.
  - The shared save (`tasks/msp/save_pipeline.lua`) takes an optional `buildPayload` per step, called when that step is queued. Adjustments uses it: it copies every changed slot when Save is pressed and builds each slot's write from its copy in turn, so a Save of many slots in the tool opened from the dashboard no longer runs into EdgeTX's instruction limit for one call. Steps that carry a `payload` behave as before.
